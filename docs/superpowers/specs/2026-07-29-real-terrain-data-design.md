# Real Terrain Data Implementation Design

| Field    | Value                          |
| -------- | ------------------------------ |
| Date     | 2026-07-29                     |
| Status   | Approved (brainstormed)        |
| Relates  | ADR-0013, ADR-0002, ADR-0007, ADR-0011, ADR-0023 |

## Problem

The game's terrain is generated by a synthetic value-noise function
(`scripts/lib/value-noise.ts`) rather than real Earth elevation data. This
causes geographic absurdities: Utah is ocean, mid-Atlantic can be land, and
mountain ranges don't align with their real-world positions. Resource deposits
(from real USGS MRDS data) can end up underwater, making them unbuildable.

ADR-0013 explicitly specifies SRTM elevation data at a sub-degree grid and
rejects procedural terrain, but the implementation was never completed — the
`fetch-geological-data.ts` script has only a stub ("requires NASA Earthdata
credentials") and the `data/geological/terrain/` directory is empty.

## Solution

Replace the value-noise terrain generator with real SRTM elevation data
downloaded from AWS Open Data (no authentication required). Downsample to a
0.25° global grid (~1M cells). Implement A* pathfinding on the elevation grid
for terrain-aware transport routing. Add terrain-based construction cost
modifiers for facility placement. Displace the 3D globe mesh vertices by
elevation data for visual authenticity.

### Design Decisions (from brainstorming)

1. **Data source:** AWS Open Data SRTM tiles (`s3.amazonaws.com/elevation-tiles-prod/srtm/`). No authentication required, unlike NASA Earthdata. Tiles are 1°×1° GeoTIFF at 1 arc-second (~30m) resolution.
2. **Grid resolution:** 0.25° (720×1440 = 1,036,800 cells). The ADR-0013 text says "0.1°" but its stated cell count (~840K) is actually ~0.278°; true 0.1° would be 6.48M rows — too large for SQLite. 0.25° is close to the ADR's 840K intent, uses clean grid alignment, and is ~15x the current 65K-row grid.
3. **Scope:** Full ADR-0013 scope — terrain data swap, terrain-aware pathfinding (A*), facility construction cost modifiers, and 3D globe visualization with vertex displacement.
4. **Pathfinding:** True A* on the 0.25° elevation grid (not great-circle scan). Finds optimal route around obstacles, returns required terrain modifiers.
5. **Existing games:** Rebuild template only. New games get real terrain; existing 16+ game DBs stay on noise terrain. No migration.
6. **Ocean bathymetry:** SRTM has nodata over ocean. Use nominal -1000m depth for all-ocean cells. Accurate bathymetry (GEBCO) is a future enhancement that doesn't require schema or downstream changes.
7. **Ocean facilities:** Deferred. `offshore_platform` / `desalination_plant` (ADR-0013) are a future spec. Ocean remains unbuildable via terraforming only.

## Architecture

### Part 1: Data Pipeline

#### New Files

##### `scripts/lib/srtm-seed.ts`

SRTM terrain seed module — parallel to `mrds-seed.ts`. Parses cached SRTM
GeoTIFF tiles and downsamples to the 0.25° grid.

**Downsample algorithm:**

1. For each output cell at 0.25° resolution (lat -90→90, lon -180→180 =
   720×1440 = 1,036,800 cells), compute its lat/lon bounds (center ± 0.125°).
2. Find which SRTM tile(s) cover that area (1° tiles, so usually 1 tile per
   cell, up to 4 at tile boundaries).
3. Read all SRTM samples within the cell bounds from the GeoTIFF(s), average
   non-nodata values → elevation. If all-nodata (pure ocean), assign -1000m
   nominal depth.
4. Round elevation to 1m precision, classify terrain class via
   `classifyTerrainClass()`, output a `TerrainCell`.

**Interface:**

```typescript
export function generateTerrainFromSrtm(
  tilesDir: string,
  config: TerrainGridConfig,
): TerrainCell[]
```

Reuses the `TerrainCell` and `TerrainGridConfig` interfaces from
`value-noise.ts` (same shape, different data source). The `seed` and
`elevationScale` / `baseFrequency` config fields are ignored; `resolution`,
`latMin`, `latMax`, `lonMin`, `lonMax` are used.

**Nodata handling:** SRTM tiles use -32768 as nodata. Skip these samples in the
average. If every sample in a cell is nodata, the cell is ocean — assign
-1000m.

#### Modified Files

##### `scripts/fetch-geological-data.ts`

Add SRTM tile download loop after the existing MRDS download:

```
- Compute the list of tile coordinates (lat -90→89, lon -180→179, 1° tiles).
- For each tile, check if cached at data/geological/terrain/srtm/srtm_{lat}_{lon}.tif.
- If not cached, download from https://s3.amazonaws.com/elevation-tiles-prod/srtm/srtm_{lat}_{lon}.tif
- Skip 404s (pure ocean tiles don't exist on the server).
- Log progress every 500 tiles.
```

~14,400 tiles cover the globe; ~7,000 contain land (others 404). Total
download ~2-4GB, cached locally. Idempotent — skips already-downloaded tiles.

##### `scripts/lib/terrain-seed.ts`

Replace the `generateTerrainGrid()` (noise) call with `generateTerrainFromSrtm()`,
with automatic fallback to the noise generator when SRTM tiles are not cached
locally:

```typescript
import { generateTerrainFromSrtm } from './srtm-seed';
import { generateTerrainGrid, DEFAULT_TERRAIN_CONFIG } from './value-noise';

// Inside seedTerrainGrid(db, config, tilesDir):
let cells: TerrainCell[];
let source: 'srtm' | 'noise';
const tilesPresent = existsSync(join(tilesDir, 'srtm')) && hasAnyTif(join(tilesDir, 'srtm'));
if (tilesPresent) {
  cells = generateTerrainFromSrtm(join(tilesDir, 'srtm'), config);
  source = 'srtm';
} else {
  console.warn('SRTM tiles not found — falling back to value-noise terrain. Run `npm run fetch:data` to download real elevation data.');
  cells = generateTerrainGrid({ ...DEFAULT_TERRAIN_CONFIG, ...config });
  source = 'noise';
}
```

The insert logic (batch insert into `terrain` table) is unchanged — same
schema, same `TerrainCell` shape. The `value-noise.ts` `generateTerrainGrid`
remains as a fallback so the build is hermetic and reproducible without the
2-4GB SRTM download. The `TerrainSeedResult` gains a `source` field
(`'srtm' | 'noise'`) so callers can log which generator was used.

##### `scripts/seed-terrain.ts`

No changes — calls `seedTerrainGrid()` which delegates.

##### `scripts/build-template.ts`

No changes to the call site (line 547-549) beyond passing the tiles dir —
`seedTerrainGrid()` delegates and logs the source. The terrain seeding line
already works; it now calls into the SRTM path when tiles are present.

##### `package.json`

Add `geotiff` dependency (pure JS GeoTIFF parser, no native deps):

```json
"dependencies": {
  "geotiff": "^2.1.0"
}
```

#### New Files (Build Scripts)

##### `scripts/build-terrain-texture.ts`

Parallel to `build-climate-texture.ts`. Reads the `terrain` table from the
template DB and generates a heightmap for the frontend.

**Output:** `public/data/geological/terrain-heightmap.json`.

**Format:** JSON object `{ width, height, minElevation, maxElevation, data }`
where `data` is a flat `Float32Array`-compatible array of elevations in
meters, row-major (lat from -90→90, lon from -180→180). This matches the
existing `forest-density.json` consumption pattern in `EarthGlobe.vue` (no
PNG decoding needed in the browser). 720×1440 = 1,036,800 values (~4MB as
JSON text; the browser parses it once at globe init).

**npm script:** `"build:terrain": "tsx scripts/build-terrain-texture.ts"`

Add to the `db:rebuild` script chain:
```
"db:rebuild": "node -e \"require('fs').rmSync('data/games/_template.db',{force:true})\" && tsx scripts/build-climate-texture.ts && tsx scripts/build-terrain-texture.ts && tsx scripts/build-template.ts"
```

### Part 2: Schema & Query Updates

#### Schema (no structural changes)

The `terrain` table schema (`server/db/schema/terrain.ts`) is already correct:
`id`, `latIndex`, `lonIndex`, `lat`, `lon`, `elevation`, `terrainClass`. No
columns to add. The only change: `latIndex`/`lonIndex` now index a 720×1440
grid (0.25°) instead of 180×360 (1°).

#### New Files

##### `lib/constants/terrain.ts`

Shared terrain constants:

```typescript
export const TERRAIN_RESOLUTION = 0.25; // degrees per cell
export const TERRAIN_LAT_CELLS = 720; // -90 to 90 at 0.25°
export const TERRAIN_LON_CELLS = 1440; // -180 to 180 at 0.25°

export function latToIndex(lat: number): number {
  return Math.round((lat + 90) / TERRAIN_RESOLUTION);
}

export function lonToIndex(lon: number): number {
  return Math.round((lon + 180) / TERRAIN_RESOLUTION);
}

export function indexToLat(index: number): number {
  return index * TERRAIN_RESOLUTION - 90;
}

export function indexToLon(index: number): number {
  return index * TERRAIN_RESOLUTION - 180;
}
```

#### Modified Files

##### `server/domains/terrain/Repositories/TerrainRepository.ts`

Update `getTerrainCellNear` to use exact index lookup instead of 0.5°
tolerance:

```typescript
getTerrainCellNear(lat: number, lon: number) {
  const latIndex = Math.round((lat + 90) / TERRAIN_RESOLUTION);
  const lonIndex = Math.round((lon + 180) / TERRAIN_RESOLUTION);
  return this.getTerrainCellByIndex(latIndex, lonIndex);
}
```

This is exact, uses the existing `getTerrainCellByIndex`, and returns at most
one cell. `getTerrainInBoundingBox` already uses lat/lon ranges and needs no
change.

##### `server/domains/terrain/TerrainService.ts`

`classifyByElevation` (lines 271-283) already matches the thresholds in
`value-noise.ts:classifyTerrainClass`. No change needed. Note: ADR-0013
specifies mountain 2000-4000m / high_mountain 4000m+, but the existing code
uses 1500-3000m / 3000m+; we keep the existing thresholds to avoid breaking
existing terraforming logic and tests. The
`getEffectiveTerrain` method works as-is with the new grid.

### Part 3: Terrain-Aware Pathfinding (A*)

#### New Files

##### `server/domains/terrain/TerrainPathfinder.ts`

A* pathfinder on the 0.25° elevation grid. Replaces the great-circle scan in
`TerrainService.getTerrainPath`.

**Grid model:** Each terrain cell is a node. Neighbors are the 8 adjacent
cells (N, S, E, W, NE, NW, SE, SW). Diagonal moves cost ×1.414 (octile
distance). Effective terrain (base + modifications) is used.

**Traversable cost per terrain class:**

| Terrain      | Base cost | Notes                           |
| ------------ | --------- | ------------------------------- |
| Ocean        | ∞         | Impassable without bridge       |
| Coastal      | 1.0       | Baseline                        |
| Plain        | 1.0       | Baseline                        |
| Hill         | 1.5       | Mild penalty                    |
| Mountain     | 5.0       | Heavy penalty; tunnel halves to 2.5 |
| HighMountain | ∞         | Impassable without tunnel       |

**Transport type modifiers:**

| Transport     | Mountain              | Ocean                  | HighMountain             |
| ------------- | --------------------- | ---------------------- | ------------------------ |
| Road/Conveyor | tunnel → 2.5          | bridge → 2.0           | impassable               |
| Pipeline      | pumping_station → 3.0 | subsea → 2.5 (shallow) | impassable               |
| PowerLine     | 2.0 (cost only)       | 1.5 (cost only)        | transmission_tower → 3.0 |

**Algorithm:**

```
1. Build a local grid slice (bounding box of from/to + 20% margin) from the
   terrain table + terrain_modifications overlay.
2. Run A* from origin cell to destination cell using transport-type-specific
   costs. Heuristic: octile distance × minimum terrain cost (1.0).
3. If no path found, return the blockers (which terrain classes made it
   impossible, at which cells).
4. Return: { path: TerrainCell[], totalCost, distanceKm, modifiers: string[] }
```

**Interface:**

```typescript
export interface PathfinderResult {
  path: TerrainCell[];
  totalCost: number;
  distanceKm: number;
  modifiers: string[]; // ['tunnel', 'bridge', etc.]
  blockers?: { terrainClass: string; lat: number; lon: number }[]; // if no path
}

export class TerrainPathfinder {
  constructor(private readonly terrainRepo: ITerrainRepository) {}

  findPath(
    fromLat: number, fromLon: number,
    toLat: number, toLon: number,
    transportType: TransportType,
  ): PathfinderResult
}
```

**Wraps around antimeridian:** If the from/to span crosses ±180° longitude,
the grid slice wraps. Implementation: if `abs(fromLon - toLon) > 180`, shift
one side by ±360.

#### Modified Files

##### `server/domains/terrain/TerrainService.ts`

`getTerrainPath` delegates to `TerrainPathfinder`:

```typescript
getTerrainPath(fromLat, fromLon, toLat, toLon, transportType?) {
  const pathfinder = new TerrainPathfinder(this.terrainRepo);
  return pathfinder.findPath(fromLat, fromLon, toLat, toLon, transportType || 'Road');
}
```

The MCP tool `get_terrain_path` (registered in `TerrainTools.ts`) gains an
optional `transportType` parameter (default `'Road'`). The response now
includes `path` (list of terrain cells), `totalCost`, `distanceKm`, and
`modifiers` (required terrain modifiers). If no path exists, returns
`blockers` with terrain class + coordinates for each obstacle.

##### `server/domains/transport/TransportService.ts`

`analyzeTerrain` (lines 122-130) currently scans a great-circle bounding box
and checks for Mountain/Ocean. Replace with a call to
`TerrainPathfinder.findPath` with the transport type. The returned `modifiers`
array populates the transport record's `terrainModifiers` field.

**`build_transport` behavior change:** Currently builds unconditionally
(only logs modifiers). After this change, `build_transport` **fails** if the
path is impossible (e.g. HighMountain with no tunnel, or deep ocean with no
bridge). The error message names the blocker terrain and the required
modifier. The LLM must terraform the obstacle or build the modifier transport
first.

The MCP `build_transport` tool description already lists all transport types
including `Tunnel`, `Bridge`, `PumpingStation`, `TransmissionTower`,
`SubseaPipeline` — these are the modifier transports the LLM builds to
overcome terrain. However, these modifier transports are **not yet
implemented** as distinct behaviors (they're just transport types in the
enum). As a v1 scope boundary: `build_transport` with type `Tunnel` or
`Bridge` succeeds and creates the transport record, and the pathfinder
treats these types as passable through their respective obstacle terrain.
Full modifier gameplay (e.g. tunnels requiring separate construction before
roads can traverse) is a future enhancement.

### Part 4: Facility Placement & Construction Costs

#### Modified Files

##### `server/domains/facilities/FacilityService.ts`

`buildFacility` (line 242-252) currently checks ocean terrain and blocks
building. Extend this:

1. **Keep the ocean check** — effective elevation ≤ 0 → error with terraform
   suggestion. No change.
2. **Add construction cost multiplier** based on effective terrain class:

   | Terrain       | Multiplier |
   | ------------- | ---------- |
   | Coastal/Plain | 1.0×       |
   | Hill          | 1.2×       |
   | Mountain      | 1.5×       |
   | HighMountain  | 1.8×       |

   The multiplier scales the construction recipe input quantities
   (concrete, steel, machinery). Apply in `ConstructionTick` when consuming
   materials: `materialCost = baseCost * terrainMultiplier`.

3. **Store the terrain class on the facility** — `FacilityRepository.create`
   (line 68) currently hardcodes `terrainClass: 'Plain'` and
   `elevation: 0`. Replace with the effective terrain class and elevation
   from `TerrainService.getEffectiveTerrain`.

##### `server/domains/facilities/Ticks/ConstructionTick.ts`

Apply the terrain cost multiplier when consuming construction materials.
Read the facility's `terrainClass` column (now populated correctly) and look
up the multiplier.

##### `server/domains/facilities/Ticks/ProductionTick.ts`

Add elevation penalty for facilities at >3000m:

```
if (facility.elevation > 3000) {
  powerThrottle *= 0.9; // 10% production penalty
}
```

Applied after the power tick sets `powerThrottle`. Simple flat penalty, no
per-recipe differentiation in v1.

##### `server/domains/extractors` (ProductionTick extractor branch)

Extractors in Mountain/HighMountain terrain get +20% throughput bonus
(hard-rock mining). Applied as a multiplier to the extractor's
`targetOutputRate`:

```
if (facility.terrainClass === 'Mountain' || facility.terrainClass === 'HighMountain') {
  effectiveRate *= 1.2;
}
```

### Part 5: Visualization

#### New Files

##### `public/data/geological/terrain-heightmap.json`

Generated by `scripts/build-terrain-texture.ts`. JSON object with a flat
row-major array of elevations in meters (720×1440 = 1,036,800 values).

#### Modified Files

##### `components/EarthGlobe.vue`

1. **Fetch the heightmap** on init, parallel to the forest/pollution texture
   fetch (line 227):

   ```typescript
   fetch('/data/geological/terrain-heightmap.json')
     .then(res => res.arrayBuffer())
     .then(buf => /* parse PNG, extract elevation samples */)
   ```

2. **Replace the base mesh** (lines 142-150). The current `IcosahedronGeometry`
   becomes a `SphereGeometry(EARTH_RADIUS, 144, 72)` (144×72 segments matching
   the 2.5°-resolution globe texture; higher subdivision for smooth
   displacement). For each vertex, sample the heightmap at its lat/lon and
   displace along the normal:

   ```typescript
   const positions = geometry.attributes.position;
   for (let i = 0; i < positions.count; i++) {
     const x = positions.getX(i), y = positions.getY(i), z = positions.getZ(i);
     const { lat, lon } = vec3ToLatLon(x, y, z);
     const elevation = sampleHeightmap(lat, lon);
     if (elevation > 0) { // only land rises; ocean stays at base radius
       const scale = elevation * 0.00002; // 8848m → ~0.177 units
       positions.setXYZ(i, x + nx*scale, y + ny*scale, z + nz*scale);
     }
   }
   positions.needsUpdate = true;
   geometry.computeVertexNormals();
   ```

3. **Wireframe overlay** (lines 153-160) uses the displaced geometry, so
   mountain ranges appear as raised wireframe patterns.

4. **Color by terrain class:** Land vertices get a subtle green-white tint;
   ocean stays dark blue (0x002233). Apply via vertex colors or a shader that
   samples the heightmap for color ramping.

5. **Coastline rendering:** The existing `buildCoastlines()` (line 70) uses
   `world-atlas` GeoJSON. This remains — real coastlines from TopoJSON. The
   terrain displacement makes coastlines align with elevation changes
   (mountains near coasts, plains inland).

6. **Globe mesh resolution:** The SphereGeometry segments (144×72) are lower
   than the terrain grid (1440×720) to keep vertex count manageable (~10K
   vertices). The heightmap is bilinearly sampled. This gives a smooth
   displaced globe without 1M vertices. For higher detail, increase to
   360×180 (~65K vertices) — testable performance tradeoff.

## Consequences

**Positive:**

- Real Earth terrain — Utah is land, Atlantic is ocean, mountain ranges align
  with real geography. Resource deposits from USGS MRDS are on the correct
  terrain.
- Terrain becomes a meaningful gameplay constraint — A* pathfinding forces the
  LLM to route around mountains and oceans, build tunnels/bridges, and plan
  transport corridors.
- Visual payoff: the 3D globe shows real mountain ranges (Himalayas, Andes,
  Rockies) as raised wireframe patterns and ocean trenches as depressions.
- Construction cost modifiers add strategic depth to facility placement —
  building in mountains costs more but extractors mine better.

**Negative:**

- SRTM download adds ~2-4GB to the build data footprint and ~minutes of
  download time on first run. Cached locally; idempotent.
- Template DB grows from ~32MB to ~50-60MB (1M terrain rows vs 65K).
- A* pathfinding adds CPU cost to `build_transport` calls. Mitigated by
  bounding-box grid slice (only loads cells near the route, not the full 1M
  grid).
- Existing games are on noise terrain — visually and mechanically
  inconsistent with new games. Acceptable per design decision (no migration).
- New npm dependency (`geotiff`) — pure JS, no native deps, but adds bundle
  size to the build scripts.

## Alternatives Considered

- **Pre-built global DEM (GEBCO/ETOPO1):** Simpler download (one file vs 14K
  tiles) but coarser source (~1km vs SRTM ~30m). Rejected — SRTM is the ADR
  source and AWS Open Data removes the auth barrier.
- **Hybrid SRTM + GEBCO bathymetry:** Best data quality (accurate ocean
  depths) but doubles the data pipeline complexity. Deferred — ocean depth
  accuracy is not gameplay-critical in v1. Can upgrade later without schema
  changes.
- **0.5° grid (minimal change):** Same row count as current, easiest swap.
  Rejected — too coarse to capture mountain ranges as distinct obstacles;
  0.25° gives much better fidelity for a manageable DB size.
- **Great-circle terrain scan (no A*):** Simpler but doesn't route around
  obstacles — just reports what's in the way. Rejected — A* gives realistic
  transport routing, a core ADR-0013 goal.
